# Queue Sheet Spec — Social Media Scheduling

The workflow reads from and writes back to **one** Google Sheet. This
file documents the column shape + sample rows so you can set up the
sheet in 60 seconds.

## Canonical header row

Paste this as row 1 of your sheet (tab-separated; Google Sheets will
expand into columns on paste):

```
post_id	channel	post_text	schedule_at	rewrite_enabled	status	posted_at	result_url	error
```

| Column | Required | Type | Read / write | Notes |
|---|---|---|---|---|
| `post_id` | yes | string | read | Operator-supplied identifier. Must be unique per `(post_id, channel)` — used as composite match key on status update. Re-using a `post_id` for a different post overwrites the prior row's audit trail. |
| `channel` | yes | string | read | One of `fb` / `li` / `discord`. Lowercase. Unknown channels are dropped silently by the filter. |
| `post_text` | yes | string | read | The source post. Posted verbatim if `rewrite_enabled` is anything other than `TRUE`. |
| `schedule_at` | yes | ISO 8601 timestamp | read | E.g. `2026-06-01T09:00:00Z`. Row fires on the first cron tick where `schedule_at <= now()`. Use `=TEXT(NOW(),"yyyy-mm-dd")&"T"&TEXT(NOW(),"hh:mm:ss")&"Z"` for "now". |
| `rewrite_enabled` | no | boolean | read | `TRUE` to run Gemini per-channel rewrite. Any other value (`FALSE`, blank, anything) = pass-through (source text posted verbatim). |
| `status` | yes | string | read + write | Operator sets to `queued` on row creation. Workflow updates to `posted` (success) or `failed` (channel API or response-shape error). Other values are ignored by the filter — useful as a manual hold (`hold`, `draft`, `pending_approval`). |
| `posted_at` | no | ISO 8601 timestamp | write | Workflow writes the time of the channel API call on success or failure. |
| `result_url` | no | string | write | Workflow writes the channel-specific URL of the live post on success. Blank on failure. |
| `error` | no | string | write | Workflow writes the channel API's error message (truncated) on failure. Blank on success. |

Any extra columns you add (notes, approver, category, …) are ignored
by the workflow — fine to use the same sheet for editorial workflow
metadata.

## Sample data — 8 rows covering the common cases

```
post-001	li	We just shipped v2 of the analytics dashboard. Three weeks of design-partner pairing; biggest unlock was in-place KPI renames.	2026-06-01T09:00:00Z	TRUE	queued
post-001	fb	We just shipped v2 of the analytics dashboard. Three weeks of design-partner pairing; biggest unlock was in-place KPI renames.	2026-06-01T09:00:00Z	TRUE	queued
post-001	discord	v2 dashboard is live — let us know if anything looks off	2026-06-01T09:00:00Z	FALSE	queued
post-002	li	Open-sourcing our prompt-eval harness today. Repo + writeup linked. Curious what the OSS community catches that we missed.	2026-06-02T07:30:00Z	TRUE	queued
post-002	discord	Open-sourced our eval harness 👀 looking for breakage reports	2026-06-02T08:00:00Z	FALSE	queued
post-003	fb	Quick note: the cohort-2 onboarding session is moving to Wednesday next week. Same time. We'll send a calendar update.	2026-06-03T12:00:00Z	FALSE	queued
post-004	li	[deliberately malformed channel: typo "linkedin" instead of "li" — workflow will drop this row silently]	2026-06-04T09:00:00Z	TRUE	queued
post-005	twitter	[deliberately unsupported channel: workflow will drop this row silently]	2026-06-05T09:00:00Z	FALSE	queued
```

**Row-by-row commentary:**

- `post-001` × 3 — canonical fan-out across 3 channels. LI + FB
  rewrite enabled, Discord pass-through (operator wrote the short
  copy directly).
- `post-002` × 2 — partial fan-out (no FB this time). Different
  `schedule_at` per channel — LI is set for 7:30am UTC (8:30am AEST,
  6:30pm PT — covers the LinkedIn morning sweet spot in two key
  TZs), Discord 30min later when the community is awake. **Use
  different `schedule_at` per channel** when channel-specific timing
  matters; that's the whole point of one-row-per-channel.
- `post-003` × 1 — single channel (FB only). Rewrite off; copy is
  already short and casual.
- `post-004` — **deliberate failure case**: channel is `li` in the
  sample column header but the `post_text` says "linkedin". The
  filter sees `channel='li'` (the column value, not the text) and
  fires normally — this row is a reminder that the workflow reads
  the column, not the post body.
- `post-005` — **deliberate failure case**: unsupported channel
  `twitter`. The filter's allowlist drops it silently. No row update
  happens; the row stays `status='queued'` forever. **Surface this
  with a monitoring query** — `count(status='queued' AND schedule_at < now() - interval '5 minutes')`
  catches malformed channel values + dead workflow alike.

## Webhook-payload alternative (no Sheet)

If you prefer to drive the scheduler from an app instead of a sheet
(useful when posts are generated by another system), swap the
**Schedule Trigger** + **Read Sheet Rows** + **Filter Queued + Due**
nodes for a single **Webhook** trigger. The webhook expects a JSON
body shaped like one of the sheet rows above:

```json
POST /webhook/social-post
{
  "post_id": "post-001",
  "channel": "li",
  "post_text": "...",
  "schedule_at": "2026-06-01T09:00:00Z",
  "rewrite_enabled": true
}
```

The downstream `Build Per-Channel Prompt` node onwards is unchanged —
the Filter node's normalisation step (lowercasing channel, parsing
boolean) is replicated as inline expression in the webhook variant.
For scheduled-in-the-future posts the webhook variant needs an
intermediate queue (postgres `posts_scheduled` per `schema.sql`) —
otherwise the workflow has nowhere to "hold" the row until
`schedule_at` arrives.

## Operator playbook

- **Adding a post:** type a new row with `status=queued` and the
  workflow picks it up on the next cron tick at or after
  `schedule_at`.
- **Holding a post:** change `status` to anything other than `queued`
  (e.g. `hold`). The filter ignores non-`queued` rows.
- **Re-trying a failed post:** read the `error` column; once fixed
  (e.g. the LI token has been rotated), flip `status` back to
  `queued`. The workflow re-posts on the next cron tick.
- **Editing copy after posting:** **don't** — `result_url` already
  points to a live channel post. Edit on the channel's own UI. The
  workflow has no "update existing post" path.
- **Bulk-scheduling:** drag-fill the `post_text` column across channels
  and the `schedule_at` column across days. Sheets handles the
  expansion; the workflow handles the per-row firing.
